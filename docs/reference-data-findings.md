# Reference dataset findings (Phase 2 investigation)

Inspected on 2026-10-13 from fresh clones, read-only (nothing from the datasets was executed or unpickled). Everything below was measured, not assumed.

> **Usage stance (owner, 2026-10-13):** Hoardware is personal-use software in a private repository that will not be shared. The licence notes below are recorded for provenance only and do not block using any of these datasets. Data files are still never committed to git. Re-verify before relying on it: the upstreams can change.

## CPU-DB (<https://github.com/zymos/cpu-db>)

**Licence.** `COPYING.txt` and the README both state the database is *Public Domain. Use as you wish.* Upstream sources are cited per row in the `Reference N` columns. (This is the maintainer's stated position; it is not legal advice.) Bundling is permitted by that statement, but the spec's approach is kept: no data ships with Hoardware, the importer reads files the user supplies.

**Currency.** Single upstream branch, last commit 2023-05-11. Treat it as a static snapshot. No release tags, so the source version recorded on import is the git commit hash (or a content hash when the files are not a git checkout).

**Which file to import.** The 82 per-vendor files `cpu-db.<Vendor>.csv` (26,558 data rows), **not** the combined `cpu-db.csv` (25,547 rows). The combined file is generated by `scripts/generate_full_cpu_list.sh` as `cat | grep | sort --unique`, which drops about 1,000 rows (259 Intel, 322 Toshiba, 132 Temic, 66 Zilog, …) and discards ordering. `supplemental_db/` holds extra tables (see below). `DEBUGTEST.csv` is a test file and must be skipped.

**Format.**
- UTF-8, no BOM, LF line endings, standard CSV quoting. No newlines inside cells. No mojibake or HTML entities found.
- 191 columns, identical header in all 82 vendor files. **The header has duplicate names**: `Empty` appears 51 times (it is the only repeated name), so `csv.DictReader` silently loses columns. Parse positionally with a name→first-index map, and fail loudly if the header differs from the expected one.
- **The README's column list is outdated** (for example it says `Frequency Max/Typ`; the files say `Frequency(internal max/typ)`). Use the real header.
- **Ragged rows**: 9,340 rows are shorter than 191 cells (trailing empties trimmed). Pad them.
- Whitespace: 2,948 cells have leading/trailing spaces. Trim.
- Placeholders: about 137k `NA` and 76k `none` cells (plus `nA`, `N/A`). These mean "not applicable", which is distinct from blank (unknown); keep the distinction, but do not show `NA` as a value.
- Values are free text with units: `150MHz`, `256KiB`, `1.2um`, dates like `September - October 1975`. Keep the raw string; parse into numbers only where search/sort needs it.
- Three rows have no Manufacturer and two have no `Part #`: skip and report as errors.

**Identity: there is no stable ID and no unique natural key.**

| Key | distinct keys | keys mapping to >1 *different* row |
|---|---|---|
| manufacturer + part # | 25,414 | 127 |
| + family | 25,447 | 96 |
| + family + stepping | 25,475 | 68 |

689 (manufacturer, part #) keys occur more than once; 561 of those are exact duplicates, but the rest are real or partial variants (for example the same Cypress part number under two families, or one fully filled row and one sparse stub). The importer therefore needs: normalise → collapse exact duplicates → keep differing rows as separate records, identified by `vendor-file | manufacturer | family | part # | variant index`, and list the ambiguous groups in the import report.

**What a record means.** One row per *marking / ordering code*, with the Q/SL spec often embedded in the part number (`A80503150 Q0939`, `BP80521180 256K SL23L`). That suits matching against what is printed on a chip, and one user-entered code will often match several rows (several steppings or spec numbers), which is exactly the "candidates for confirmation" case.

**Completeness is uneven.** Of the combined rows: Family 98%, Chip Type 74%, Frequency 72%, Package 67%, L2 cache 63%, Core Stepping 36%, CPUID 42%, Socket 32%, Core 21%, Release date 2%. Many Pentium-era rows hold only part number, frequency and package. The UI must never assume a field exists. The upstream TODO lists Intel as 50% and AMD as 10% complete. Retro rows present: AMD K5 15, K6 119, Athlon 573, 486-class 42; Cyrix 109; IDT 100; VIA 102; Intel 386 121, 486 255, Pentium-family 2,594.

**Supplemental: `cpu-db.supplemetal.Intel.S-Spec_numbers.csv`** (6,182 rows: family, S-Spec, speed, bus speed, package, part number + 6 alternates, cpu-world.com reference). Valuable for identifying Intel CPUs by the S-Spec printed on the chip, but it joins poorly to the main file (only 1,128 of 5,969 part numbers appear there) and family names differ (`80486` vs `486`). Better treated as an alias source than as a join. Out of scope until decided.

**Photo columns** (`Photo front filename N`, creator/copyright…) reference images that are not part of the data. Ignore them.

## GPU datasets

Both candidates are scrapes of TechPowerUp's GPU specs. Neither contains add-in-board (AIB) variants.

### dbgpu (<https://github.com/painebenjamin/dbgpu>)

- Licence: MIT, which covers the *code*. The data comes from TechPowerUp; its terms were not reviewed and the MIT grant should not be assumed to cover scraped data.
- The git repository contains **no data**. The database is `data.pkl`, a pickle bundled in the PyPI package (and `.gitignore`d). A pickle must never be loaded from an untrusted source; only the JSON/CSV exports that `GPUDatabase.from_file` also accepts are acceptable inputs.
- Manufacturers: NVIDIA, AMD, Intel, ATI, 3dfx, Matrox, XGI, Sony. No S3, Cirrus Logic, Trident, Tseng, Oak, etc. About 2,000 entries, started from 1986.
- Granularity: chip/reference-product level (`GeForce GTX 1080` + GPU `GP104`), with a field list that includes reference board length, connectors and so on.

### GPUs-Specs (<https://github.com/RonnyMuthomi/GPUs-Specs>)

- **No licence file and no README**, a single commit (2025-11-16), one 2 MB CSV (`gpu_1986-2026.csv`) plus a notebook that only loads it. No stated provenance, though the column names and the `source_file` column (`1986.json` …) show it is TechPowerUp-derived. With no licence, reuse rights are unclear: it should not be bundled, and using it needs the user's own judgement.
- 3,203 rows × 134 columns (sparse; mobile/integrated variants in separate column groups). Rows are well-formed (all 134 wide). Brands: NVIDIA 1,436, AMD 850, ATI 603, Intel 220, Matrox 35, 3dfx 16, XGI 15, SiS 11, Sony 9, S3 6, VIA 2.
- Retro coverage is thin: by release decade 1980s 7, 1990s 109, 2000s 1,089. `Board Design__Board Number` is filled for 1,413 rows and `Part Number` for only 15 (AMD `102-Dxxxxx` style numbers).

### Board-level suitability (the spec's critical rule)

Neither dataset can identify a board. `Brand` is always the chip vendor; probing the names: `viper` 0, `diamond` 0, `zotac` 0, `stealth` 0, `trio64` 0 (but `voodoo2` 2, `riva tnt2 ultra` 1, `millennium` 12, `rage pro` 5). A Diamond Viper V770 Ultra or a Zotac factory-overclocked card has no counterpart, only its chipset (RIVA TNT2 Ultra) does. So **both are usable only as chipset-level reference data** (GPU chipset maker + chipset), linked as a *candidate* and never presented as exact board specs, which is precisely rule 4 of the matching precedence. ATI's own early cards are the exception, as ATI sold its own boards, but they are still ATI reference products.

## Consequences for the design

1. Importers are CLI-driven and read user-supplied local files; nothing is downloaded and no data is bundled.
2. Reference records need: kind (`cpu`, `gpu_chipset`, …), upstream identity string, content hash (for added/changed/unchanged reporting), raw specs as JSONB, per-import provenance (source id, name, URL, licence, source version, imported-at).
3. CPU-DB: parse positionally, pad, trim, keep `NA`/blank distinct, dedupe exact duplicates, report ambiguous groups.
4. GPU: keep only the adapter interface in v0.1; a chipset-level adapter over a user-exported JSON/CSV can follow once a licence position is chosen.


## Update: the S-Spec table is now used

`supplemental_db/cpu-db.supplemetal.Intel.S-Spec_numbers.csv` (6,182 rows: S-Spec, speed, bus speed, L2 size, package, order code) is read by the importer when present. Matching main records (joined on the S-Spec token inside their part number, Intel only) gain **Bus speed** and any speed/cache/package they lacked; the main file's own values always win. S-Specs absent from the main files become records of their own (`sspec|<code>`, about 1,260). Measured on the real data: 4,271 existing records changed, 1,262 added, 26,806 in total, and a repeat import changes nothing. The table has the same limitation as the main file: no marketing names ("300A"), no socket or stepping.
